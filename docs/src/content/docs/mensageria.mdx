A **mensageria** é o broker Mosquitto do serviço `mqtt-broker`. Por ela passa
o que dispara comportamento: a sinalização que o `aop-cc` adquire da emissora simulada, as trocas de
usuário e de serviço, os eventos dos objetos do carrossel, as camadas da tela e os pop-ups. O que precisa ser consultado a qualquer momento fica no Redis
([Modelo de dados Redis](../modelo-redis/)); um dado com as duas naturezas vive nos dois.

O broker tem um plugin que confere o esquema de cada publicação ([Esquema das mensagens](#esquema-das-mensagens)).
Ele não controla o acesso a tópicos: qualquer cliente assina e publica em qualquer tópico
([Escopo, limites e decisões](../escopo/#de-arquitetura)).

## Conectar ao broker

| De onde | Endereço |
|---|---|
| um serviço em container, na rede do Docker | `mqtt://mqtt-broker:1883` |
| um processo no computador | `mqtt://localhost:1883` |
| a página da TV, no navegador | `ws://<host da página>/mqtt`: a casca repassa a conexão ao WebSocket do broker |
| um cliente WebSocket de fora, para depurar | a 9001 do broker, em porta escolhida pelo Docker (`docker compose port mqtt-broker 9001`); `MQTT_WS_PUBLISH=<porta>:9001` no `.env` da raiz a fixa |

- O `/mqtt` só existe no host da casca: a aplicação de emissora, servida no host dela, não alcança o
  broker.
- Os clientes do testbed assinam com *no local*: ninguém recebe a própria publicação.

## Os tópicos

Cada ramo junta os tópicos de mesmo prefixo, e cada nome mostra se o tópico fica retido, se não tem
esquema e se ainda não tem publicador no testbed. O `<sid>` é o `globalServiceId` do serviço, e o
`<serviceId>`, o número do serviço na SLT. A emissora simulada não publica nada: o `aop-cc` busca o que ela
serve ([Emissora simulada](../emissora-simulada/)) e distribui. Como a TV reveza os pop-ups está em
[aop-shell](../aop-shell/#pop-ups).

### Retenção

- **Estado** (`currentUser`, `currentService`, `services`, `graphics-application`, os `tlm/` menos os
  `tlm/object/`): retido, para que quem conecta depois saiba o estado. Publicar vazio apaga o retido.
- **Evento** (pop-ups, `removedUser`, `application-state`, `end-request`, `tlm/object/`): não retido; só
  recebe quem está escutando.
- **Camadas da tela:** não retidas. A página que reabre não recebe a última camada.

As mensagens retidas sobrevivem à reinicialização do broker. `docker compose down -v` as apaga, junto
com os perfis criados.

## Esquema das mensagens

O plugin confere o payload de cada publicação num tópico com esquema declarado e recusa o que não o
cumpre: a mensagem não chega a quem assina.

| Publicação | Conferida |
|---|---|
| num tópico com esquema, com payload | sim |
| num tópico sem esquema | não |
| com payload vazio (a limpeza de uma retida) | não |
| em `errors/*`, `$SYS/*` e nos tópicos do teste de latência | não |

- **Onde estão os esquemas:** `infra/mqtt-broker/plugin/config/schemas.json`, uma chave por tópico,
  exato ou com `+` e `#`. Vale a chave igual ao tópico; sem ela, a primeira chave com curinga que casa,
  na ordem do arquivo.
- **Texto puro:** num tópico de esquema `"type": "string"`, o payload que não é JSON vale inteiro como
  texto (um UUID, uma URL). Um payload que é JSON vale pelo valor: `"abc"`, com aspas, é o texto `abc`.
- **JSON estrito:** o payload tem de ser exatamente um texto JSON. Sobra depois do valor, comentário,
  aspas simples ou vírgula sobrando dão `INVALID_JSON`.

O esquema é um subconjunto do JSON Schema Draft-07:

| Palavra-chave | Para |
|---|---|
| `type`, `enum`, `const` | todos os tipos |
| `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf` | número |
| `minLength`, `maxLength`, `pattern` (regex POSIX) | texto |
| `minItems`, `maxItems`, `uniqueItems`, `items` | array |
| `minProperties`, `maxProperties`, `required`, `properties`, `additionalProperties` | objeto |

As demais palavras-chave (`oneOf`, `anyOf`, `allOf`, `not`, `if`, `format`, `$ref` e outras) são
ignoradas sem aviso: a regra que depende delas não é conferida.

### Erro de validação

A publicação recusada sai no log do broker (`Validation failed for topic <tópico>: <motivo>`) e em
`errors/<client_id>`, sem retenção:

```json
{"timestamp": "AAAA-MM-DDTHH:MM:SS", "topic": "...", "error_type": "INVALID_JSON | SCHEMA_VALIDATION_FAILED",
 "details": "...", "client_id": "...", "payload": "..."}
```

- A mensagem tem no máximo 2047 bytes; quando o payload é cortado, ela leva `"truncated": true`.
- No `<client_id>` do tópico, `+`, `#`, `/` e caracteres de controle viram `_`. O campo `client_id`
  da mensagem leva o original.

### Acrescentar ou mudar um esquema

1. Edite `infra/mqtt-broker/plugin/config/schemas.json`.
2. Reconstrua o broker, na raiz do TV30. O plugin só lê o arquivo na partida, e o arquivo entra na
   imagem no build: `docker compose restart` não basta.

   ```bash
   docker compose --profile mqtt build mqtt-broker
   docker compose --profile mqtt up -d mqtt-broker
   ```

3. Confira no log que o arquivo carregou:

   ```bash
   docker logs mqtt-broker 2>&1 | grep -E "Schemas? loaded"
   ```

   Sai `Schemas loaded from file: <n> topics configured`. Com o arquivo em JSON inválido, sai só
   `Invalid JSON in schemas file`, e o broker sobe **sem nenhum esquema**.

Para conferir uma regra, assine `errors/#` e publique um payload que a viole:

```bash
mosquitto_sub -h localhost -p 1883 -t 'errors/#' -v &
mosquitto_pub -h localhost -p 1883 -i meu-cliente -t aop/currentService -m '{"x":1}'
```

## Teste de latência

O plugin responde a uma publicação em `PublisherResponseTime<id>/iteration<N>` com
`{localtime, id, iteration, diffTime}` em `PluginResponseTime<id>/iteration<N>`. O medidor, com
interface web ou sem ela, fica em `infra/mqtt-broker/brokertimetest/`. Os testes do plugin estão em
[Como testar](../como-testar/).
